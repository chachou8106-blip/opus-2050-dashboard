## Pourquoi le garde-fou n'a pas joué

Le champ du 208 est :

```
{{trim(replace(replace(replace(replace(ifempty(207.data.candidates[1].content.parts[1].text; "{}"); "```json"; emptystring); "```"; emptystring); newline; emptystring); tab; emptystring))}}
```

`ifempty` ne protège que du **vide**. Une réponse vide devient `{}` et le run continue.
Une réponse **présente mais malformée** passe telle quelle dans ParseJSON, qui casse.
Les cinq Sages ont exactement le même montage (202, 204, 206, 208, 210) : la même
panne peut venir de n'importe lequel.

Et dans tout le scénario, **aucun des 80 modules n'a de gestionnaire d'erreur** —
vérifié, `onerror` est vide partout. Il y a 14 modules `ParseJSON` (202, 204, 206,
208, 210, 302, 304, 306, 402, 9998, 9997, 10010, 10014, 20016) : chacun peut arrêter
le run entier.

## Ce que je n'ai pas pu voir

Le contenu exact renvoyé par le 207. L'API Make ne donne pas les entrées/sorties par
module ; seul le panneau OUTPUT de l'historique d'exécution, dans l'interface, les
montre. **C'est la seule source de vérité** (règle du 27/08).

Ce que la configuration permet de dire sans l'avoir vu : le corps du 207 demande à
Gemini `"responseMimeType":"application/json"` avec `"maxOutputTokens":2000` et
`"thinkingConfig":{"thinkingBudget":0}`. Avec `responseMimeType` en JSON, Gemini ne
peut normalement pas renvoyer de prose — **sauf si la réponse est coupée** en
atteignant les 2000 jetons, auquel cas le JSON arrive tronqué et ParseJSON échoue
avec ce message précis. C'est l'hypothèse la plus probable, ce n'est pas une
certitude : à confirmer sur le panneau OUTPUT du 207 (chercher `finishReason`).
